# WebDAV Downloader

Go-приложение рекурсивно скачивает файлы с WebDAV-сервера, сверяя уже сохраненные файлы и создаёт HTML-отчёт.

## Запуск локально

Требуется Go 1.22 или новее. Внешних зависимостей нет.

Скопируйте `.env.example` в `.env`, укажите параметры сервера и запустите:

```sh
make run
```

Или соберите исполняемый файл:

```sh
make build
./bin/webdav_sync_tool
```

Остановка по Ctrl+C или SIGTERM: приложение дожидается активных загрузок.

### Запуск через docker-compose

Образ запускает [supercronic](https://github.com/aptible/supercronic), который по расписанию из `/etc/crontab` вызывает `/app/webdav_sync_tool`. Расписание по умолчанию — понедельник, 03:00 (файл `crontab` в репозитории).

```sh
cp .env.example .env   # укажите параметры WebDAV
docker compose up -d
```

- Переменные берутся из `.env`; `VAULT_DIR` в compose-файле принудительно задан как `/vault`.
- Файлы сохраняются в `./downloads` на хосте (том `./downloads:/vault`).
- Чтобы изменить расписание, отредактируйте `crontab`, раскомментируйте в `docker-compose.yml` строку `./crontab:/etc/crontab:ro` и перезапустите контейнер: `docker compose up -d --force-recreate`.
- Логи: `docker compose logs -f`.

### Архитектура

Синхронизация работает с двумя абстрактными хранилищами (`Storage`, [src/fs_storage.go](src/fs_storage.go)): источником и назначением. По умолчанию источник — WebDAV, назначение — диск (`VAULT_DIR`); при `SYNC_MODE=fs_to_webdav` — наоборот. Алгоритм ([src/sync.go](src/sync.go)) одинаков в обоих режимах, особенности вынесены в реализации ([диск](src/fs_storage_disk.go), [WebDAV](src/fs_storage_webdav.go)):

- `ReadDir` — содержимое каталога: вложенные каталоги и файлы (путь, размер, MD5, дата изменения);
- `Open` / `Put` — чтение файла и создание файла по пути (каталоги создаются автоматически; запись через `<файл>.tmp` с проверкой MD5 и размера, затем замена оригинала);
- `Copy` — копирование внутри хранилища (для дубликатов);
- `Remove` — перемещение в `.trash` с записью `.state.json` и строк `TRASH.md`;
- `PurgeTrash` — окончательное удаление просроченных файлов из `.trash`.

Пути в хранилищах отсчитываются от корня: для WebDAV это `WEBDAV_REMOTE_PATH`, для диска — `VAULT_DIR` + `WEBDAV_REMOTE_PATH`. `.trash` лежит в корне хранилища.

### Режим webdav_to_fs (по-умолчанию)

Назначение: бекап файлов webdav сервиса в файловой системе и периодическая синхронизация.

1. Полностью строится дерево WebDAV.
2. Строится дерево файловой системы.
3. Файлы, совпавшие по MD5 получают `completed`.
4. Ищутся переименования. Для оставшихся `pending` файлов, отсутствующих на диске, ищется локальный файл с тем же MD5 — он копируется на нужное место (исходный не удаляется).
5. Далее смотрим, сколько файлов поменяли HASH. Если слишком много - возможно это хакеры. Сначала считается суммарный размер всех файлов с несовпавшим ETag; если он превышает `REPLACE_WARN_PERCENT`, ни один из них не заменяется и создаётся `REPLACE_WARN.md`. Иначе файлы заменяются по одному, затем докачиваются недостающие. Скачивание идёт в `<файл>.tmp`; после проверки MD5 оригинал удаляется и tmp переименовывается. При любой ошибке tmp удаляется.
6. Файлы, которых нет на сервере, перемещаются в папку `.trash` (см. `DELETE_WARN_PERCENT`); список — в `.trash/TRASH.md` и служебный `.state.json`.
7. Из `.trash` окончательно удаляются файлы, удалённые `TRASH_RETENTION_DAYS` дней назад и ранее. Дата удаления хранится в `.trash/.state.json` (на диске или на сервере в зависимости от режима); MD5 и размер берутся из самих файлов корзины. Файл, которого нет в `.state.json`, считается удалённым только что, и дата сразу сохраняется. Реализации корзины не выходят за пределы `.trash`: пути проверяются (`..` и служебные `TRASH.md`, `.state.json` отклоняются). 
8. Так же удаляются отчёты `download-report-yyyyMMdd.html` и строки таблиц служебных md-файлов старше срока `TRASH_RETENTION_DAYS`.

### Режим `fs_to_webdav`

Деревья WebDAV и файловой системы строятся так же (без служебных файлов и `.trash` в обеих сторонах), но источником считается файловая система:

1. Локальные файлы, совпавшие по MD5 с ETag на сервере, получают `completed`.
2. Для файлов, отсутствующих на сервере, но с таким же MD5 у другого файла сервера, выполняется `COPY` на стороне сервера.
3. Файлы с несовпавшим ETag заменяются (если не превышен `REPLACE_WARN_PERCENT` от размера файлов в файловой системе), затем загружаются недостающие. Загрузка идёт `PUT` в `<файл>.tmp` на сервере; после проверки MD5 (если ETag сервера — MD5) и размера выполняется `MOVE` с перезаписью оригинала. При ошибке tmp-файл на сервере удаляется.
4. Файлы сервера, которых нет в файловой системе, не удаляются (`DELETE` не вызывается), а перемещаются (`MOVE`) в `<WEBDAV_REMOTE_PATH>/.trash/` на сервере; список — в `.trash/TRASH.md` на сервере. Если их размер превышает `DELETE_WARN_PERCENT` от размера файлов на сервере, создаётся `DELETE_WARN.md`.
5. Из `.trash` на сервере окончательно (`DELETE`) удаляются файлы старше `TRASH_RETENTION_DAYS` дней — это единственное место, где вызывается `DELETE` для файлов данных.

Служебные md-файлы (`REPLACE_WARN.md`, `DELETE_WARN.md`, `DOWNLOAD_ERROR.md`) и отчёт в этом режиме по-прежнему создаются в папке `VAULT_DIR`. Файлы в каталогах сервера, которые не удалось прочитать (`error`), не меняются.

Служебные файлы в корне папки назначения: `download-report-yyyyMMdd.html`, `REPLACE_WARN.md`, `DELETE_WARN.md`, `DOWNLOAD_ERROR.md`, `.trash/`; они не участвуют в сравнении.

Ошибки скачивания (в том числе несовпадение MD5) переводят файл в статус `error` и обрабатываются отдельной очередью с повторами. Если все попытки исчерпаны, файл добавляется в таблицу `DOWNLOAD_ERROR.md` в корне папки назначения (путь, дата, размер в МБ, код ошибки: HTTP-статус, `MD5` или `ERR`).

Файл `download-report-yyyyMMdd.html` (суффикс — текущая дата) в папке назначения обновляется раз в 30 секунд и сохраняется в последний раз по окончании цикла работы, после чего программа завершается. В отчёте отображаются папки до второго уровня, общий размер и процент завершённых файлов; папки с ошибками выделяются красным, полностью скачанные — зелёным.
